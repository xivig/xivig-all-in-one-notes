:: Laravel Tips :19 ::
Components
Components and slots provide similar benefits to sections, layouts, and includes; however, some may find the mental model of components and slots easier to understand. There are two approaches to writing components: class based components and anonymous components.

To create a class based component, you may use the make:component Artisan command. To illustrate how to use components, we will create a simple Alert component. The make:component command will place the component in the app/View/Components directory:

php artisan make:component Alert

The make:component command will also create a view template for the component. The view will be placed in the resources/views/components directory. When writing components for your own application, components are automatically discovered within the app/View/Components directory and resources/views/components directory, so no further component registration is typically required.

You may also create components within subdirectories:

php artisan make:component Forms/Input

The command above will create an Input component in the app/View/Components/Forms directory and the view will be placed in the resources/views/components/forms directory.

If you would like to create an anonymous component (a component with only a Blade template and no class), you may use the --view flag when invoking the make:component command:

php artisan make:component forms.input --view

The command above will create a Blade file at resources/views/components/forms/input.blade.php which can be rendered as a component via <x-forms.input />.

To generate the controller inside the Admin folder (i.e., App\Http\Controllers\Admin\AuthorController), you can specify the full namespace path when using the make:model command. Here's how you can do it:
php artisan make:model Author -mcr --factory -s --controller=Admin/AuthorController

Alternatively, if you've already created the model and just want to generate the controller in the Admin namespace, you can run:
php artisan make:controller Admin/AuthorController --resource --model=Author

This will create a resource controller at app/Http/Controllers/Admin/AuthorController.php and link it to the Author model.

```bash
php artisan make:component HomeLayout --view
```

1. Run:
   ```bash
   php artisan make:component HomeLayout
   ```

2. Then manually move or rename the view file:
   ```bash
   mv resources/views/components/home-layout.blade.php resources/views/layouts/home.blade.php
   ```

3. And update the `render()` method in `HomeLayout.php`:

   ```php
   public function render()
   {
       return view('layouts.home');
   ```

:: Laravel Tips :23 ::
Great question — and the answer depends on your use case in Laravel. Let's break it down:

---

### 🔘 `@yield`: Best for Layouts

- Use when you have a **layout file** (`layouts/app.blade.php`) and want child views to insert content.
- Requires a matching `@section` in the child view.

**Example:**

_In `layouts/app.blade.php`:_

```blade
<body>
    @yield('content')
</body>
```

_In `home.blade.php`:_

```blade
@extends('layouts.app')

@section('content')
    <p>This is the homepage</p>
@endsection
```

---

### 🧩 `{{ $slot }}`: Best for Blade Components

- Use inside a **Blade component**, like when using `<x-layout>` tags.
- It's simpler, faster, and **doesn’t need section names** — just drop content inside the component.

**Example:**

_In `components/layout.blade.php`:_

```blade
<body>
    {{ $slot }}
</body>
```

_In your Blade file:_

```blade
<x-layout>
    <p>This is the homepage</p>
</x-layout>
```

---

### 🧠 Which to Use?

- **Use `@yield`** when extending traditional layouts.
- **Use `{{ $slot }}`** when working with modern Blade components (like `<x-app-layout>`).

Both are excellent tools — it’s just a matter of whether you prefer layout inheritance (`@extends/@section/@yield`) or the cleaner component approach (`<x-*>` with `$slot`).

Named slots let you pass multiple chunks of content into specific areas of a component.

**Component (`card.blade.php`):**

You can nest components and pass slots down the tree.

**Parent Component (`modal.blade.php`):**

You can even pass **named slots into nested components**, like a `<x-slot name="footer">` inside a modal.

### 🧩 1. Dynamic Slot Names

You can dynamically name a slot using `:name` and a variable:

```blade
@php $slotName = 'footer'; @endphp

<x-slot :name="$slotName">
    <p>This is the dynamic footer slot.</p>
</x-slot>
```

In your component:

```blade
<div class="card">
    {{ $header ?? '' }}
    <div class="body">{{ $slot }}</div>
    {{ $footer ?? '' }}
</div>
```

This lets you conditionally inject content into different areas of a component — great for flexible layouts or dashboards.

---

### 🧬 2. Slot Components (Composable Slots)

You can pass entire components into slots:

```blade
<x-modal>
    <x-slot name="header">
        <x-alert type="warning">Heads up!</x-alert>
    </x-slot>

    <p>This is the modal body.</p>
</x-modal>
```

This is especially powerful when your slot content needs to be styled or interactive — like buttons, alerts, or nested modals.

---

### 🧠 3. Slot Macros (Reusable Slot Templates)

While Blade doesn’t have native “slot macros,” you can simulate them using components or includes:

```blade

<div class="alert alert-{{ $type }}">
    {{ $slot }}
</div>
```

Then use it inside a slot:

```blade
<x-slot name="header">
    <x-slots.alert type="info">
        Welcome back!
    </x-slots.alert>
</x-slot>
```

This keeps your slot content clean, reusable, and DRY.

:: Laravel Tips :30 ::
Eloquent Eager Loading & Preventing the N+1 Query Problem

The N+1 problem occurs when fetching a list of models and then querying a relationship in a loop:
// BAD: 1 query for posts + N queries for author (N+1 queries!)
$posts = Post::all();
foreach ($posts as $post) {
    echo $post->author->name;
}

// GOOD: Always eager load relationships using with() (Only 2 queries!)
$posts = Post::with('author')->get();

// Eager load multiple relationships & nested relations:
$posts = Post::with(['author', 'category', 'comments.user'])->get();

// Lazy Eager Loading (if you already have the collection):
$posts->load('author');

// PRO TIP: Automatically prevent lazy loading in development:
// Add to app/Providers/AppServiceProvider.php in boot():
Model::preventLazyLoading(! app()->isProduction());

:: Laravel Tips :36 ::

When processing huge datasets, never use all() or get() to prevent memory exhaustion!

3. cursor(): Uses PHP PDO generator; loads ONE model at a time into memory:

:: Laravel Tips :100 ::
Laravel Clean Architecture & Best Practices Checklist

1. Thin Controllers, Rich Domain:
   Controllers should only handle HTTP concerns: validate input, call an Action or Service, and return response.
   Move complex business logic into single-responsibility Action classes (`app/Actions/CreateInvoiceAction.php`).

2. Use Form Requests for all non-trivial validation instead of controller inline validation.

3. Always Eager-Load Relationships (`with()`) to prevent the N+1 query performance trap.

4. Never use `env()` outside of `config/` files. Always use `config('services.key')`.

5. Use Database Transactions (`DB::transaction`) whenever writing to multiple related tables.

6. Protect Sensitive Columns with `$hidden = ['password', 'remember_token']` and `$fillable`.

7. Keep your routes organized using route groups, resource controllers, and dedicated route files.

8. Run optimization commands in production (`config:cache`, `route:cache`, `view:cache`).
